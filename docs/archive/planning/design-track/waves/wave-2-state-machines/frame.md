# Problem Frame — Wave 2: Jig's run and work-item state machines

> Intake artifact for the DDD-first deep-design track's Wave 2. It frames the **lifecycle /
> state-machine** altitude of jig ahead of the three Wave 2 story briefs:
> `w2-s1-work-item-lifecycle`, `w2-s2-run-lifecycle-and-recovery`, and
> `w2-s3-invariant-catalog`. It records source evidence, InputResolution, the AgreedSystemModel,
> architecture mode, and initial DDD depth before authoring. Produced by applying the
> `technical-design` pack's `frame-technical-design` skill; the next stage is
> `author-technical-design`, gated on this frame's approval status.
>
> This frame consumes Wave 1's settled domain model
> ([`../wave-1-domain/frame.md`](../wave-1-domain/frame.md),
> [`../wave-1-domain/decisions.md`](../wave-1-domain/decisions.md) D-001..D-003, and the two Wave 1
> story briefs) rather than re-deriving it. Where Wave 1 named entities and lifecycle _terms_,
> Wave 2 sequences those terms into transition tables, guards, events, and recovery semantics —
> the altitude Wave 1's own source map explicitly deferred to this wave.

## 1. Scope and Goal

- **Source request:** deep-design track, Wave 2 — frame jig's run and work-item **state
  machines** at the altitude of transition tables, guards, events, and recovery/resume semantics,
  over the entities Wave 1 already settled. Two lifecycle areas: the **work-item state machine**
  (eligible → started → parked → done | landed | rejected | blocked, its guards, and the events
  each transition emits) and the **run state machine** (previewed → started → stopped | resumed |
  completed, plus recovery/resume semantics: the RESUME family, storage preflight, crash/restart,
  and GUARD-1 launch-binding immutability across a resume). A third area consolidates the
  invariant catalog these two produce.
- **Goal:** produce an `AgreedSystemModel` clean and citable enough to seed the Wave 2 charter and
  the three story briefs, and to be read by later waves' frames without rework. The model must
  name, as **candidates** (not closed answers): states, events, guards, and recovery semantics for
  both lifecycles; the runtime authorization guards (Fence/Doorbell) that gate work-item
  transitions; and the invariant candidates the state machines mint, continuing the `INV-*` ledger
  from `INV-009`.
- **Out of scope for this wave:** the closed transition tables themselves (drawing the final,
  authoritative table per state machine is the future design session's job, prescribed by the
  story briefs this frame seeds — not this frame); field-level schema or a frozen contract for the
  execution plan or the observability records (both remain v0, unfrozen); package/module layout;
  any code, TypeScript interfaces, or JSON Schema; the four driver-seam ports (Wave 3); deepening
  `records.md`'s storage engine, `authorization.md`'s capability-attestation depth, or
  `bootstrap.md`'s provider-wiring rules beyond what recovery/resume semantics need as a pointer
  (all remain later-wave or same-wave-story territory per their own stub notes).

### Lifecycle and State Terms

Per calibration point 4, this wave's frame records lifecycle terms **plus candidate transitions,
guards, and events** — still short of the closed transition table, which is the future authoring
session's job.

- **Work item candidate states** (unchanged from Wave 1 / `orchestration.md`): `eligible →
started → parked (transient) → done | landed | rejected | blocked`. Candidate guards: dependency/
  eligibility resolution (ISO-1) gates `eligible`; the Fence's grant/deny/route gates `started`'s
  exits (grant → proceed toward `done`; deny → `blocked`; route → `parked`); evidence-met (MERGE-1/
  MERGE-3) gates `done`; the runner-exclusive merge action gates `landed` (MERGE-2/MERGE-4); an
  owner decision resolves `parked` to resume or `rejected`.
- **Run candidate states** (unchanged from Wave 1 / `orchestration.md`): `previewed → started →
stopped | resumed | completed`. Candidate guards: storage preflight (RESUME-4) gates `started`;
  an unattended `parked` work item or a liveness signal (LIVE-1/2) drives `stopped`; owner
  re-approval on safety-relevant change (RESUME-5) and GUARD-1 launch-binding immutability gate
  `resumed`; all work items reaching a terminal outcome without a needed human gates `completed`.
- **Recovery/resume candidate semantics:** durable progress survives a crash (RESUME-1); resume
  restarts from the last safe checkpoint, not from zero (RESUME-2); irreversible actions already
  taken are recognized and not repeated (RESUME-3, no-double-effect); an inability to safely
  continue parks in a named, inspectable state rather than guessing forward (RESUME-4); and a
  resume across a changed safety-relevant assumption requires fresh owner re-approval and evidence
  (RESUME-5) — candidates this wave names, the future session sequences into a closed guard set.
- **GUARD-1 across resume (candidate):** the policy/work-profile/repo-floor bindings fixed at
  launch (Wave 1, INV-003) must remain immutable across a resume — named here as a candidate
  invariant for `w2-s3` to consolidate, not yet a closed rule.

## 8. Architecture Mode and Initial DDD Depth

**Selected architecture_mode:** `lifecycle/state-machine`

**Why this mode fits:** Wave 2's deliverable is explicitly state terms, transition authority, and
recovery shape — the discriminating description the altitude ladder gives for this mode ("state
terms, transition authority, retries, or recovery shape the design"). This is a deliberate shift
from Wave 1's `system-entity-model`, whose deliverable was ownership and relations, not sequencing.
`orchestration.md` already draws a closed Mermaid transition table for the work-item lifecycle —
concrete evidence the design has already moved past entity-model altitude for this area; Wave 2's
job is to give that same rigor to the run lifecycle and to recovery/resume, which `orchestration.md`
and `bootstrap.md` both explicitly leave as prose or named-but-undesigned extension points.

**Selected depth:** `use-case-slices`

**Why this depth fits:** Wave 2's deliverable — transition tables carrying states, events, and
guards — is qualitatively deeper than Wave 1's `strategic-only` (bounded-context ownership and
vocabulary only, no transitions). The discriminating test from the coordinator's own brief: "the
artifact carries states + events + guards → deeper than `strategic-only`." `use-case-slices` fits
because Wave 2's commands are a small, named set with explicit input/output contracts and domain
errors — the same shape `runtime-design-m5a.md` itself selected `use-case-slices` depth for over
this exact runtime behavior (§4, and its own command table: ValidatePlan, PreviewRun, StartDryRun,
ResolveEligibility, AuthorizeRequest, RecordRunnerOwnedAction, RecordEvent, TransitionStory,
CompleteRun). This wave does **not** reflexively copy Wave 1's `strategic-only` depth, and does
**not** jump to `tactical-ddd`: M5a's own precedent explicitly defers aggregates/domain-event
ceremony for this lifecycle "until a slice exercises concurrency (ISO-4), resume (RESUME-\*), rich
policy, and real drivers" — and while Wave 2 is the first wave to substantively frame resume, it
does so at the run-lifecycle/guard-candidate altitude, not by standing up a Run aggregate with
transactional consistency rules; concurrency (ISO-4) and real drivers remain untouched (Wave 3/4b).
`ports-and-adapters` depth is not selected: Wave 2 does not isolate the domain from a concrete
infrastructure choice — that is Wave 3's job for the four driver seams.

**Where tactical depth is intentionally omitted:** no aggregate, value-object, or domain-event
ceremony is authored this wave for either lifecycle, even though this is the first wave to
substantively frame resume (a traditional tactical-DDD trigger per the depth ladder's "complex
lifecycle transitions... consistency model" criterion). This is a deliberate deferral, following
M5a's own precedent of recording "why not" rather than defaulting to it: concurrency (ISO-4) and
real drivers — the two complexity drivers M5a named as the actual gate for escalating past
`use-case-slices` — remain out of scope for Wave 2 and land in Wave 3 (ports) and Wave 4b
(provider parts). A later wave may escalate depth for the run/work-item lifecycle deliberately,
once those drivers are in play, exactly as M5a itself modeled.
