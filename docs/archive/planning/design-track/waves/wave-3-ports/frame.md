## 1. Scope and Goal

- **Source request:** deep-design track, Wave 3 — frame jig's **ports**: the boundary contracts
  between jig-core and the world. Two areas: the four **provider/driver seams** (Agent, Execution
  Host, Forge, Work Source — `contracts/providers.md`) and the **data + driving ports** (the
  `PlanValidator`/`RunStore` data ports on one side, per `core/plan-intake.md` and
  `core/records.md`; the operator/control-plane driving surface on the other, per
  `contracts/driving.md`). This is the wave that makes the **boundary rule** enforceable: core
  owns ports, invariants, state machines, the authority model, and event semantics; providers
  implement against ports and must not redefine core policy, evidence, authorization, or state
  semantics.
- **Goal:** produce an `AgreedSystemModel` clean and citable enough to seed the Wave 3 charter and
  the two story briefs, and to be read by later waves' frames (Wave 4a core parts, Wave 4b
  provider parts) without rework. The model must name, as **candidates** (not closed contracts):
  each port's owns/implements split, its anti-corruption stance, its seam invariants, and the
  candidate new port-boundary invariants this wave surfaces — continuing the `INV-*` ledger from
  `INV-009` (coordinated with Wave 2's own not-yet-assigned candidates, per Wave 2's `w2-s3`
  consolidation checkpoint, so the two waves' candidates do not collide when both consolidate).
- **Out of scope for this wave:** closed port contracts, method signatures, TypeScript interfaces,
  or JSON Schema for any port (the future design sessions this wave's stories seed author those);
  field-level schema or a frozen shape for the execution-plan or observability-records contracts
  (both remain v0, unfrozen, per `contracts/README.md` and the two contract docs themselves);
  package/module layout; the Fence's internal classifier mechanics (`authorization.md`, Wave 2
  territory, cited here only as an already-named port this wave inventories but does not
  redesign); the work-item and run state machines themselves (closed in Wave 2); deepening
  `records.md`'s storage engine, `bootstrap.md`'s provider-wiring rules, or `authorization.md`'s
  capability-attestation depth beyond what the port skeleton needs as a pointer (Wave 4a's
  "core parts" territory, per the track's wave table); any actual provider adapter (Wave 4b);
  conformance-suite mechanics or provider manifest format (`providers.md` already names both as
  deferred, unclaimed by this wave).

## 8. Architecture Mode and Initial DDD Depth

**Selected architecture_mode:** `ports-and-adapters`

**Why this mode fits:** Wave 3's deliverable is explicitly boundary contracts that isolate jig-core
from concrete infrastructure — the four provider seams, the two data ports, and the one driving
port — the discriminating description the altitude ladder gives for this mode ("the domain must be
isolated from databases, provider SDKs, queues, HTTP frameworks, or other concrete infrastructure").
This is a deliberate shift from Wave 2's `lifecycle/state-machine`, whose deliverable was transition
tables with states, guards, and events, not boundary isolation. The four driver seams sit exactly at
this wave's altitude because `contracts/README.md` already draws them as the edge distinct from
`core/` ("core is not a seam"), and `runtime-design-m5a.md` itself selected `ports-and-adapters` at
this exact seam set within an otherwise `use-case-slices` design (§4: "The driver seams require
ports-and-adapters because guarantee 4... makes Agent/Execution Host/Forge/Work Source swappable
authority boundaries"). This is not still `lifecycle/state-machine` (Wave 2), because no new state
or transition is authored this wave — only the invocation **points** within Wave 2's already-closed
tables are named. It is not yet `tactical-ddd`, because no aggregate, value-object, or domain-event
ceremony is warranted: the complexity driver this wave answers is anti-corruption isolation, not
rich lifecycle/consistency rules over a domain aggregate.

**Selected depth:** `ports-and-adapters`

**Why this depth fits:** the depth ladder's required elements for this rung — "domain/application
ports, adapter responsibilities, composition/wiring boundary, contract tests or mocks that are held
to the real seam" — match this wave's deliverable precisely: each port's candidate method shape
(domain port), its owns/implements split (adapter responsibilities), bootstrap as the cited
composition/wiring boundary, and the two v0 contracts as the seam a future contract test would hold
adapters to. This wave does **not** reflexively copy Wave 2's `use-case-slices` depth: Wave 2's
depth fit its command-shaped deliverable (named transitions with guards); Wave 3's deliverable is
boundary contracts, which the ladder places one rung further along a different axis (isolation, not
sequencing). This wave does **not** jump to `tactical-ddd`: the ladder's `avoid` guidance for
`ports-and-adapters` ("allowing adapters to define domain vocabulary or persistence models to leak
inward") is itself this wave's central anti-corruption concern, and satisfying it does not require
aggregates or domain events — those remain deferred until a slice exercises concurrency (ISO-4) or
real provider adapters (Wave 4b), exactly the gate M5a itself named for this same seam set.

**Where tactical depth is intentionally omitted:** no aggregate, value-object, or domain-event
ceremony is authored this wave for any port, even though ports are a traditional locus for adapter
implementations that might later warrant richer modeling (e.g., a capability-attestation aggregate,
a provider-manifest value object). This is a deliberate deferral, following both M5a's and Wave 2's
own precedent of recording "why not" rather than defaulting to it: concurrency (ISO-4) and real
provider adapters — the concrete drivers that would justify tactical ceremony over a port boundary —
remain out of scope for Wave 3 and land in Wave 4b (provider parts). A later wave may escalate depth
for a specific port deliberately, once those drivers are in play.
