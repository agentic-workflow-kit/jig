# Problem Frame — Wave 4b, s5: Agent provider

> Intake artifact for the DDD-first deep-design track's Wave 4b, part 1 of 4. It frames the
> **Agent provider** — the contained coding worker that reads a work item, writes code, runs
> checks, and reports — the first of four PROVIDER parts this wave deepens. Produced by applying
> the `technical-design` pack's `frame-technical-design` skill; the next stage is
> `author-technical-design`, gated on this frame's approval status. Authored alongside three
> sibling frames (`w4-s6-execution-host-provider.md`, `w4-s7-forge-provider.md`,
> `w4-s8-work-source-provider.md`) in one pass for mutual coherence; cross-references to those
> parts are by part id, and cross-references to prior waves name the wave explicitly (never a
> bare `D-###`).
>
> This frame consumes [Wave 3's ports frame](../../wave-3-ports/frame.md) (the Agent port's
> candidate shape and anti-corruption stance, already deepened at port-skeleton altitude in
> `docs/design/contracts/providers.md`) and all four of Wave 4a's committed frames — especially
> [`w4-s1-records-observability`](../../wave-4a-core/frames/w4-s1-records-observability.md) (the
> records/evidence surface as this wave's frame-time contract) and
> [`w4-s2-plan-policy-evidence`](../../wave-4a-core/frames/w4-s2-plan-policy-evidence.md) (the
> evidence/attestation category model, EARN-2) — plus Wave 4a's
> [`decisions.md`](../../wave-4a-core/decisions.md) D-001..D-007. Wave 4b is the wave where the
> governing plan's provider-boundary rule, adopted for this wave in [`../decisions.md`](../decisions.md)
> D-004, is tested against a real provider adapter for the first time: providers implement against
> ports and must not redefine core policy, evidence, authorization, or state semantics. `AGENTS.md`
> remains repo-contract context for that guardrail.

## 1. Scope and Goal

- **Source request:** deep-design track, Wave 4b, story 1 — deepen the **Agent port's** section of
  `docs/design/contracts/providers.md` in place: the contained worker's request/observe surface,
  the structural (not merely policy) guarantee that it holds no privileged method, and the
  **stub-vs-real-driver posture** — only the scripted-worker stub is built first; the real agent
  driver is a named, visible extension point.
- **Goal:** produce an `AgreedSystemModel` for the Agent provider clean and citable enough to seed
  this wave's charter and story brief, coherent with the three sibling parts (especially the
  shared seam with `w4-s6`: the worker runs _inside_ the execution host), and consistent with the
  boundary rule and Wave 4a's committed core contracts.
- **Out of scope for this part:** the Agent port's method signature itself (Wave 3 already
  candidate-named `requestAction`/`observe`-shaped access, cited not redesigned); the Fence's
  `authorize` classifier (`w4-s3`, cited); the evidence/attestation category model and its
  freshness/staleness rule (`w4-s2`/`w4-s3`, cited — this part supplies attestation _claims_, never
  judges them); the Records engine's consistency model (`w4-s1`, cited); the Execution host's
  containment/isolation model (`w4-s6` — this part only states that it runs inside a host, not how
  that host contains it); the conformance suite mechanics and provider manifest format (both
  explicitly deferred by `providers.md` itself, unclaimed by this wave per Wave 3's D-001);
  concrete model/prompt-strategy choices (Work profile, Wave 1's D-001, owner-authored content);
  field-level schema, TypeScript, or JSON Schema; package/module layout.

### Seams and External Boundaries

- **The Agent port** (Wave 3, candidate-named, cited) — this part deepens the adapter-level
  anti-corruption detail behind the port, not the port's own method shape.
- **The execution-host containment seam (s5 ↔ s6)** — the Agent port's adapter runs inside the
  execution host; this part states only that containment exists and is the worker's environment,
  never how strong it is or how it is verified (that is `w4-s6`'s SEC-2 territory). Stated
  consistently with `w4-s6`'s frame.
- **The attestation-claim seam (s5 → w4-s2/w4-s3)** — this part supplies capability-attestation
  claims; `w4-s2` owns the category taxonomy those claims are expressed against, `w4-s3` owns the
  freshness/staleness judgment. This part never defines either.
- **The Fence boundary** (cited, Wave 2/Wave 3/`w4-s3`, unchanged) — every worker request is
  authorized before it executes; this part does not redesign the classifier.
- **The Records boundary** (cited, `w4-s1`, unchanged) — every request/observe/report outcome is an
  event; this part does not define the log's consistency model.
- **The stub/real-driver boundary** — only the scripted-worker stub is a built adapter this wave;
  the real agent driver is a named, visible extension point, per the track's Stub rule.
