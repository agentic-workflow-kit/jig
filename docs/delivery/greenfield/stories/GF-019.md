# GF-019 — Work Source semantic contract

## Outcome, value, and why now

Deliver the design-owned Work Source exchange and exact `SCH-PLAN` validator, exercised only by a
scripted hostile fixture. It gives the Envelope Builder validated candidate work without allowing a
provider or any candidate to create a Run. This is the earliest safe source seam for GF-021 and
GF-022; a concrete source, provider configurability, approval, intake, and dispatch remain
impossible.

## Governing paths and stable IDs

`envelope-production.md` owns `EP-SOURCE`, `EP-TRACK`, the one-track rule, plan validation, and
the rule that changed source bytes are a new candidate. `mechanism-and-provider-contracts.md` owns
repeatable source exchange, `BND-WAIT-MECHANISM`, and `BND-RETRY`; `data-and-identity.md` owns
`ID-SOURCE-REQ`, `SCH-SOURCE-EXCHANGE`, and `SCH-PLAN`. `runtime.md` keeps the Builder outside
core authority. `delegation-register.md` limits `DR-4` and `DR-12` to transport/channel realization
below these semantics. `CF-ENVELOPE`, `CF-MECH-SOURCE`, and the versioned hostile source corpus
are the conformance oracles.

## Dependencies plus start evidence

Start only when GF-002's merged identity/canonical-byte evidence proves `ID-SOURCE-REQ` and
versioned boundary validation, and GF-004's merged harness evidence can record exact fixture,
suite, build, and probe digests. Reconfirm the selected baseline commit and tree
`763fa777c62999795fb679cc05a61be1190d93b6`, the `PORT-SOURCE`/Builder boundary, and current
`DR-4`/`DR-12` records. A branch, an asserted fixture pass, or a concrete provider claim is not
start evidence.

## In-scope and non-goals

In scope: request/result schemas, canonical request basis, stable request/item/revision/cursor and
content/provenance validation, exact plan graph/criteria/resource-demand validation, retry state,
and one scripted fixture. Exclude structured JSON files, YAML/legacy guessing, provider manifests,
capability proofs, policy/profile/setup composition, user approval, `SCH-ENVELOPE`, `LG-INTAKE`,
and all Run/controller/effect behavior.

## Runtime/product unit, ports, inputs, outputs, identities, persisted facts, authority

The external Envelope Builder invokes inbound `PORT-SOURCE`; the scripted fixture returns facts
only. It validates one canonical `ID-SOURCE-REQ` over source/provider/request/basis, then accepts
only `SCH-SOURCE-EXCHANGE` with stable item key, revision/cursor, content digest, provenance, and
one versioned `SCH-PLAN`. The Builder is the sole validator and produces an unapproved candidate
and diagnostic projection; no durable authority fact is written. Source and fixture may observe
and return bytes, never choose policy, approve, transition, publish, dispatch an Operation, or
create `ID-RUN`. The port type, construction guard, and test-only fixture registration keep every
other adapter unreachable.

## Observable success and terminal outcomes

Success is a byte-stable accepted exchange bound to its exact request, whose plan has an acyclic
graph, existing stable dependency keys, well-formed done conditions referencing frozen-policy
check classes, requirements/criteria, safe-point demand, feasible reserves, and exactly one track.
It releases only source input to composition. Invalid, stale, cross-request, ambiguous,
noncanonical, oversized, provenance-mismatched, changed-content, timeout, retry-exhausted, or
unverifiable input is `Rejected`/`NotRun` pre-Run with a typed record. No state can become Run,
Accepted, dispatched, or landed in this story.

## Failure, uncertainty, timeout, retry, reconciliation, recovery, cleanup, and resume

Malformed or wrong-boundary input is `FC-INPUT`/`FC-SUBJECT`; transport failure or deadline is
`FC-MECHANISM`. Each request has immutable `BND-WAIT-MECHANISM` (configured only in its declared
5s–2h range) and `BND-RETRY` (1–5, default 3); each retry retains the same request identity and
records its ordinal. Exhaustion rejects envelope production before a Run. A lost response is
reconciled by the same request/cursor/revision exchange, never by treating unknown bytes as the
old result; changed revision/content is a fresh candidate. Recovery reconstructs recorded request
basis and bound consumption; missing or conflicting facts fail closed. The fixture has no external
effect, credential, allocation, cleanup, or active-session resume path.

## Security and trust: validation, credentials, redaction, and authority widening

Limit request and plan sizes, depth, Story/dependency/check counts, strings, and graph work; reject
duplicate keys, unknown versions/fields, noncanonical bytes, path traversal-like provenance, and
cross-track references. No credential is accepted or stored. Fixture bytes and diagnostics are
redacted/quarantined as hostile input and retain only digest/provenance needed for evidence.
Provider output is untrusted candidate input: it cannot carry an approval, manifest, proof,
authority, or fallback. The only adapter is an explicitly test-only scripted registration, so an
unqualified implementation cannot be configured or dispatch an effect.

## Deliverables without delegated algorithm invention

Own semantic source port/schema/validator, scripted hostile fixture, fixtures, and evidence
recorder under the eventual source/testkit boundaries; document their immutable fields and failure
taxonomy. `DR-4`: Engineering/configuration may choose an in-process typed transport only; owner is
the delegation register, evidence is `CF-MECH-SOURCE`, fallback is no configured provider, and no
authority may move. `DR-12`: Engineering/configuration may realize a channel only after its port
suite; selected option here is scripted fixture, fallback is reject/unavailable. Neither permits
an invented parser, provider policy, or source semantics.

## Test and evidence obligations

Run deterministic schema/canonical vectors; plan graph, dangling-edge, cycle, done-condition,
requirement/criteria, track, demand/reserve, and provenance tests; hostile limits and unknown-field
tests; request/revision/cursor/digest replay and permutation tests; timeout/retry/lost-response
recovery matrix; and negative-authority tests proving no `ID-RUN`, ledger, approval, or dispatch.
Record fixture/source identity, canonical bytes/digests, suite/probe/build/version, bound
consumption, result, and exact candidate digest for `CF-ENVELOPE` and scripted `CF-MECH-SOURCE`.
Provider E2E is omitted because no real provider is reachable.

## Exact acceptance

An independent reviewer receives the exact candidate content digest, baseline/target basis,
fixture and corpus digests, suite/probe/build metadata, failure matrix, delivery metadata, and
`CF-*` findings. They require no unresolved finding and the selected deterministic scripted
verification posture. Acceptance records only review of this package; authoritative landing still
requires the separate merged commit/CI proof and exact-candidate review. Stale, self-authored,
partial, or differently bound evidence is rejected.

## PR boundary, relative size, and split

closed oracle; a concrete provider is separately GF-020.

## Definition of Done

- Versioned canonical inputs reject unknowns and bind the exact request/result/plan.
- Bounded retry/recovery and every stated pre-Run rejection are evidenced; no effect exists to retry.
- Required deterministic, hostile, replay, timeout, and authority tests plus `CF-*` evidence pass.
- Exact evidence, `git diff --check`, repository checks/CI, and independent review pass; no provider
  is configurable.
