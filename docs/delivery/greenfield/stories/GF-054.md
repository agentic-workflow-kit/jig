# GF-054 — Private first-party SDK facade

## Outcome, value, and why now

Offer one stable-in-repository, private TypeScript SDK facade for approved operator workflows:
preview, approvals, start, inspect/watch/why, decide, suspend/resume/stop, notices, and export.
It lets CLI and MCP consume owning ports without bypassing them. It follows completed durable
semantics; it creates neither public semver promise, new authority, nor direct controller/store API.

## Governing paths and stable IDs

`runtime.md` owns the six-unit topology and private `PORT-CONSUMER`/`RT-OPERATOR` boundary. `DR-7`
selects private TypeScript SDK with thin CLI/stdio consumers; it forbids a public surface or facade
authority crossing. The facade must carry existing schema IDs from its delegated owning ports, not
invent command/event identities.

## Dependencies plus start evidence

Require exact merged GF-023/024 envelope and intake, GF-036--038 decision/lifecycle/obligation,
GF-051 projection, GF-052 notices, and GF-053 export evidence. Confirm every delegated operation
has a current owning-port contract, authenticated configured principal path, and exact suite output.
No provider is assumed qualified merely because the SDK compiles.

## In-scope and non-goals

In scope is a typed private facade and contract parity adapters over existing ports. Excluded are
direct ledger/controller/store access, public package publication, multi-tenant/public service,
new workflow semantics, scheduler/webhook input, credentials in request objects, and provider
qualification.

## Runtime/product unit, ports, inputs, outputs, identities, persisted facts, authority

`RT-OPERATOR` owns the facade and delegates to `PORT-CONSUMER` then the correct intake/decision/
publish/artifact port. Inputs use existing versioned schemas, principal binding, request correlation,
and limits; outputs preserve exact owning-port result/status IDs. SDK stores no durable truth:
ledger/artifact/registry facts remain authoritative and projections remain read-only. The caller is
one configured principal; SDK may propose/request but cannot approve, decide, dispatch, publish,
finalize, or observe beyond the port's authorization. Type shape and convenience methods cannot
widen authority.

## Observable success and terminal outcomes

Success is SDK calls whose result, refusal, redaction, terminal condition, and durable causal record
are identical to direct owning-port behavior. `Blocked`, `Parked`, `Rejected`, `NotRun`, and
`Stopped` are surfaced exactly and never normalized to success. SDK has no terminal lifecycle of its
own; unknown method/version/principal yields a typed fail-closed refusal.

## Failure, uncertainty, timeout, retry, reconciliation, recovery, cleanup, and resume

Validate malformed/version-skew as `FC-VALIDATION`, principal mismatch as `FC-AUTHORITY`, unavailable
port as `FC-MECHANISM`, and stale request/fence as rejection before dispatch. The facade records no
effect intent itself; it delegates stable Operation identity, bound, reconciliation and retry rules
to the owning port. It never retries an uncertain effect; callers receive its parked/reconcile state.
After crash it reconstructs no truth, reconnects only with a fresh authorized request, drops local
cache, and cannot resume or clean a Run except through the existing authorized operation.

## Security and trust: validation, credentials, redaction, and authority widening

Canonicalize schemas and bound payload/stream sizes; bind configured caller identity at the facade
boundary. Credential names resolve in the owning runtime only in memory and are neither SDK fields
nor logs. Preserve port redaction and scope checks; reject unknown/ambiguous proof. No SDK fallback,
provider result, or generated type can expose an unqualified adapter or mint a grant.

## Deliverables without delegated algorithm invention

Deliver private SDK types, facade implementation, port delegation map, error/result mapping,
redacted test fixtures, and consumer contract evidence. `DR-7`: owner Arye; selected private TS
facade; constraints private/no direct internals/no public compatibility guarantee; evidence parity
fixtures; fallback remove the facade rather than expose internals; blast radius consumers only. Any
new method semantics/protocol requires `OWNER_DECISION_REQUIRED`.

## Test and evidence obligations

Run compile/schema/version negatives, delegation-map contract tests, configured/cross-principal
authority tests, redaction/oversize tests, all workflow result parity tests, stale/fenced/replay
calls, port-fault propagation, stream interruption/reconnect, and SDK-to-ledger causal binding tests.
Update `CF-CONSUMER` with exact candidate/build/schema/fixture/result digests. Provider and full E2E
qualification are inapplicable here because the SDK cannot admit a provider.

## Exact acceptance

An independent reviewer checks exact candidate/target and SDK/API digest, owning-port mapping,
negative authority/redaction outputs, and `CF-CONSUMER` evidence. Any direct internal access,
semantic divergence, public promise, or unbound result fails. Acceptance remains separate from
merge/CI landing evidence.

## DR choices

`DR-7` records question/private consumer facade, owner Arye, selected private TS option, immutable
constraints, parity evidence, no-facade fallback, and limited consumer blast radius; public API or
additional authority is deferred and requires owner decision.

## PR boundary, relative size, and split

M, one private consumer-to-port parity oracle. Expected operator SDK/types/tests; excludes CLI/MCP
transports and provider realization. No split: a facade without its parity contract is not useful.

## Definition of Ready

- Listed owning ports and durable workflows are merged, exact, and independently evidenced.
- Principal binding, schema versions, redaction, method map, DR-7 boundary, and oracle are fixed.

## Definition of Done

- SDK delegates only, stores no truth, exposes no new authority, and preserves owning-port terminal semantics.
- Required schema, authority, fault, replay, redaction, parity, and consumer evidence passes.
- Exact-candidate review, `git diff --check`, repository checks, CI, and landing proof pass.
