# GF-001 — Private Node/TypeScript workspace substrate

## Outcome, value, and why now

After exact owner activation, create the proposed private Node/TypeScript/pnpm/Turbo substrate that
can express the approved runtime seams as a hermetic dependency graph. It releases repeatable local
and CI validation, affected-task caching, and failure isolation before any Jig behavior is made
reachable. This is the earliest safe point because later stories need one reviewed graph in which
semantic packages and test evidence can be isolated. It does **not** release a runtime, CLI, port,
provider, storage implementation, or lifecycle authority. Until activation, this is a planning
story only and must stop with `OWNER_DECISION_REQUIRED`.

## Governing paths and stable IDs

- [`runtime.md`](../../../redesign/design/runtime.md) fixes the six-unit deployment shape and requires authority to remain in the controller rather than in tooling or stores.
- [D10](../../../redesign/design/decisions/D10-runtime-decomposition.md) owns the private modular package decomposition decision; `DR-2` records its implementation-realization choice.
- [`architecture-conformance.md`](../../../redesign/design/architecture-conformance.md) is the
  governing source for `DR-8`: it makes versioned conformance evidence a gate, not a test-report
  convention, and bounds the private deterministic testkit/harness realization.

`DR-2` delegates the private package-layout realization while preserving D10's authority seams; `DR-8` delegates the deterministic private testkit/harness realization. `PC-JIG-16` requires reusable conformance proof before trust while testkit packaging remains open, so this story supplies hermetic evidence lanes without choosing package names or counts. `PC-JIG-20` requires a user-run, non-hosted runtime boundary, so the workspace must not introduce hosted control-plane authority. No imported commitment is assigned. No runtime semantic identifier is assigned to this tooling-only story; adding one would falsely create product behavior.

## In-scope and non-goals

In scope after explicit selection: private workspace roots, the selected Node/TypeScript/pnpm/Turbo
configuration, project references, explicit task inputs/outputs, immutable CI action references,
dependency-boundary rules, and hermetic fixtures for cache and failure-isolation proof. GF-001 also
owns the fail-closed transition of the source-empty repository guard to the exact activated private
tooling allowlist: it must admit only the ratified workspace/tooling paths required here and continue
to reject product source, runtime, provider, adapter, and package behavior.

Out: product schemas; controller code; any runtime unit; ports/transports; credentials; source, ledger, artifact, session, workspace, verification, or delivery adapters; package names/counts that would pre-empt a later approved seam realization; public publishing; registry configuration; and cleanup of a prior generation. A package exists only when a later story has a bounded owner and acceptance oracle.

## Runtime/product unit, ports, inputs, outputs, identities, persisted facts, authority

The unit is a private build/test workspace, not `SYS-JIG`. It exposes no product port and cannot import, instantiate, or configure an adapter. Inputs are checked-in non-secret configuration and fixture sources; outputs are local/CI task artifacts and cache metadata, neither authoritative nor durable Jig facts. The CI/workspace identity may label a build, but it cannot mint a product event, transition, Operation, or provider capability.

The only authority is build orchestration: it may schedule declared tasks, never decide a Jig lifecycle. The fence is structural: dependency rules reject a task/package edge that crosses an undeclared future seam; no task may inject credentials, expose a runtime entrypoint, or dispatch an external effect. `RT-CONTROLLER`, stores, and `RT-OPERATOR` are absent, so none can gain power here.

## Observable success and terminal outcomes

Success is a clean checkout where declared private tasks are reproducible, an affected-change fixture runs only its declared dependents, and an intentionally failing lane cannot make an unrelated lane appear successful. The durable evidence is a versioned CI/local report bound to the exact source/content digests and toolchain lock state; it releases GF-002's codec implementation dependency.

Terminal outcomes are `Passed` or `Failed` build evidence, not Run/Story outcomes. `Blocked`, `Parked`, `Rejected`, `NotRun`, `Stopped`, acceptance, landing, and dispatch are impossible because this story creates no Run, controller, or effect path.

## Failure, uncertainty, timeout, retry, reconciliation, recovery, cleanup, and resume

Malformed configuration, lockfile drift, forbidden imports, missing declared outputs, nondeterministic task inputs, or a failed fixture fail the task closed. These are build failures, not product failure records. CI retry may re-execute the whole hermetic task from immutable inputs, but it cannot reuse an uncertain external effect because none exists. Cache loss is recoverable by recomputation; cache hits are advisory and never proof of a pass. Cleanup may remove only disposable build outputs under the workspace policy; it must not erase checked-in evidence. Resume reruns from source and lockfile, with no persisted Jig state to reconstruct.

## Security and trust: validation, credentials, redaction, and authority widening

Validate configuration schema, lockfile integrity, package-edge allowlists, task input/output declarations, and immutable CI action references. Install/build scripts run with least privilege; credentials are neither required nor accepted by test fixtures. Logs redact environment values and never persist secrets. A cache, CI provider, plugin, or future adapter is untrusted evidence until its declared task verifies it. No configuration switch may turn an unqualified adapter into a task dependency or runtime command; such paths remain absent/unreachable.

- The source-empty guard transition to the exact activated GF-001 tooling allowlist, with negative

## Test and evidence obligations

Run deterministic workspace install/compile/config tests; static forbidden-edge tests; cold/warm
affected-cache fixtures; a deliberately failing independent-lane fixture; and positive/negative
source-empty-guard fixtures for the exact activated tooling allowlist. Contract, replay, crash,
timeout, recovery, provider, and E2E product tests are N/A: no product contract, durable fact,
clock, adapter, or effect is reachable; the structural absence is proven by the graph guard and
inspection. Record separately: immutable planning provenance commit/tree and the clean normative
comparison; explicitly authorized scope and constraints; current product/design/track provenance;
dynamically observed execution base ref/commit/tree and the empty
predecessor-containment proof; toolchain/lockfile digests; task definitions; exact implementation
candidate commit/tree; fixture inputs and outputs; and the selected final-verification posture,
policy-selected required check-class set, verification configuration/environment, and subject
binding. No conformance suite is claimed; GF-004 supplies the catalog and recorder.

## Exact acceptance

An independent reviewer separately verifies immutable planning provenance and its clean 67-file
comparison; explicitly authorized scope; current product/design/track provenance;
the dynamically observed target base ref/commit/tree and empty predecessor-containment result; the
exact implementation candidate commit/tree and merge-base equality; lockfile/toolchain metadata;
graph and static-guard reports; source-empty-guard allowlist and negative results; cache and
failure-isolation evidence; and that no runtime or adapter entrypoint was added. Required findings
are resolved; an exact owner decision may close only an `OWNER_DECISION_REQUIRED` finding by
supplying the missing active authority, and cannot waive a blocking defect. Stale, self-authored,
partial, or differently bound evidence fails. The reviewer's exact-candidate approval records
`Accepted` only.
It binds GF-001's implementation tuple and never widens authority, scope, integration, or landing.
The selected verification intent is then recorded on authorized entry into `Finalizing`;
under `deterministic`, every policy-selected required check class must produce a passing,
subject-matching `EV-CHECK-OBSERVATION`, and the complete required set must be satisfied there
before any target-changing Operation. `none` is an explicit no-op. Those post-`Accepted`
observations are authorized continuation evidence, not a review-invalidating edit, while the
reviewed candidate, posture, required class set, verification configuration/environment, and
subject binding remain unchanged; drift in any one requires a fresh tuple and review. Authoritative
landing remains separate target proof.
